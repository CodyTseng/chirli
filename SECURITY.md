# Security policy

Chirli is an unreleased MVP. It has not had an independent security audit. No supported-release or response-time commitment has been established.

## Reporting

A private vulnerability-reporting channel has **not yet been configured**. Before public release, maintainers must enable and verify a private reporting mechanism on the chosen repository host and document its exact use here. There is no security email address or repository URL to infer from this checkout or from PsstPsst's authors.

Do not publish live credentials, private messages or a weaponized exploit in a public issue. Prepare a minimal local reproduction with disposable keys, affected version/mode, expected/actual behavior, impact and relevant sanitized diagnostics. Once a verified private channel is documented, send that reproduction through it. No bounty, SLA or external coordination agreement is promised here.

## Boundaries

- The decoder verifies the giftwrap, seal, rumor hash, author and one-to-one recipient before exposing text. Default identity-key NIP-17 and explicit split-key mode both accept verified standard and NIP-4E envelopes; the legacy compatibility:false flag only suppresses identity-key declaration publication. Known unrelated own key declarations block publication; discovery freshness is bounded by relays/cache, not globally guaranteed. See docs/INTEROPERABILITY.md.
- Database payloads use AES-256-GCM only when storageKey is supplied; otherwise payloads/keyrings are explicitly tagged plaintext without cryptographic tamper protection; public routing metadata and status/timestamp indexes remain visible. Core Bot does not store identity signing secrets; the live application can persist a generated signer in a private adjacent file. Split encryption keys and pending declarations follow the configured plaintext/encrypted codec. Preserve the original storageKey whenever encryption is enabled. Protect storage keys, files, backups, process memory and your own logs.
- Incoming rumor IDs deduplicate protocol receipt, not arbitrary external side effects. Failed/incomplete business work can run again. Relay acceptance means neither delivery nor reading.
- Historical and self-copy messages do not run live handlers. A new subscription, including one after AUTH, treats frames before EOSE as history. Downtime messages may be synchronized without executing old commands.
- Untrusted relay URLs come from signed metadata or application configuration. The SDK makes outbound WebSocket connections to them; applications deploying in restricted networks must enforce their own destination policy. There is no built-in SSRF allowlist or tenant boundary.
- Identity signers must sign the exact requested template. Both modes retain identity-key crypto for standard peers; split mode adds generated/imported current, pending and legacy local keys. Neither mode supplies forward secrecy or key-vault isolation by itself.
- Error observers can see verified message context and application errors. Observer failures are ignored so monitoring cannot crash message processing; sanitize logging and handle telemetry failures in your application.

One active process/client per account database, including across modes, is supported. Synchronous storage and crypto execute on the Node thread, and received-event history/dispatch queues are not a production-grade resource admission system. Full archive enumeration, undecryptable-envelope retention, storage-key migration, distributed workers and application authorization are outside this MVP. See README and API.md before deployment.

The checked-in CI uses only disposable/local protocol tests. Actual public relays, mobile apps, external bunker products and hardware signers and production deployments require separate assessment. No real AI provider or external tool execution is part of this SDK.

Managed subscriptions reconnect with bounded backoff and overlap paging; raw transport alone does not. Recovered envelopes never execute live commands, and incomplete scans leave checkpoints unchanged. A remote signer sees plaintext used in NIP-44 operations. Its operational failures are surfaced and stop recovery checkpoint advancement. Opaque remote decryption errors are conservatively treated as retryable, so corrupt signed wrappers can also leave a remote scan incomplete; there is no durable raw-envelope quarantine or product-specific error classification. See SIGNERS.md and RECOVERY.md.

Registered NIP-CD definitions are always public on configured write relays. Bot startup reconciles its account's complete registry, including deleting old definitions absent locally. Register every module before starting one account owner. Ordinary Clients do not own catalogs or modify user-installed kind 10992 lists. All write-relay queries/publications must succeed before Bot startup completes. An unavailable or known truncated snapshot never becomes deletion evidence. Metadata/scopes grant no execution permission, and public withdrawal cannot erase cached copies.

Explicit keyRotation configuration authorizes scheduled public encryption-key declarations while started. Candidates are durable before publication; ACK failure keeps pending custody and retries the same event. Retired-key count/optional age pruning happens only after successful rotation. Evicted keys cannot decrypt unseen old envelopes; SQLite/WAL/backups are not securely erased. Known foreign declarations require explicit locally held-key migration, never forced overwrite. Relay/cache checks are not a globally fresh account lock. See [key custody and migration](docs/KEYS.md).

Custom MessageStorage implementations receive encoded messages, processing state and public routing metadata, never storageKey, keyrings, evidence or outbox records. They are trusted for durable unique insertion, state updates and account isolation; losing or changing done states can cause repeated handling. With storageKey, payloads are ciphertext; without it they are readable plaintext. Internal SQLite retains only temporary message handoffs until insertion succeeds. Protect both stores and follow docs/STORAGE.md. Multiple-relay discovery can be partial; cached evidence is not a globally fresh declaration guarantee. At least one ACK is not all-relay replication. See docs/RELAYS.md.

Bot allowlist is checked against the verified seal/rumor identity in both modes before new history, peer evidence or business callbacks. Anonymous wrapper authors and separated n encryption keys grant no authorization. Empty lists deny all external incoming senders; absent lists preserve open intake. Rejected new rumors have no durable denial receipt, so policy changes can admit later live presentations. Revoked pending business work is consumed without callbacks; old history remains readable. Crypto/remote signer work and operational error monitoring still occur before a hidden sender can be authenticated. This inbound policy is not an outbound ACL or rate limiter. See [access](docs/ACCESS.md).

The optional live-example initializer creates a fresh bot nsec/storageKey in an ignored 0600 .env file; this is operator credential storage, separate from SDK keyring persistence and not a hardware vault. Live runners intentionally read operator configuration only when explicitly started, publish their own key/relay metadata and registered public commands and respond to permitted DMs. They do not print incoming text, credentials or bunker authorization URLs. Protect config/database backups. Automated tests use generated temporary configs and local relays only.

Zero-config live startup reuses/creates a 0600 identity file beside the database and logs only public keys. That file is encrypted if CHIRLI_STORAGE_KEY is provided, otherwise plaintext. It is never overwritten to fix parsing/key/mode errors. Existing databases without their generated signer file require the original signer to avoid silently changing accounts. Default public relays match PsstPsst; testing does not connect to them. Plaintext persistence assumes trusted filesystem/backend contents, including pending business records. Initial wire signature/author validation and NIP-44 encryption remain mandatory in either storage mode.

Built-in RelayError diagnostic fields expose only origin, operation/code, whitelisted network/reason codes and numeric statuses/kinds. Relay paths/queries/credentials, raw rejection bodies, AUTH challenges and message text are withheld. The live formatter does not print arbitrary application Error.message/stack and bounds aggregate recursion. Explicit custom application logging remains the application's responsibility. Read-only operator connectivity diagnostics do not require a private key or event publication.

Automatic NIP-4E device sync is enabled by default. Only verified requests signed by the exact account identity can export held separated keys, and only encrypted 4455 responses are published. Identity signing secrets are excluded. This headless policy authenticates signing capability, not human presence; permission to sign 4454 is secret-transfer authorization. Use keySync:false / CHIRLI_KEY_SYNC=0 if this is unsuitable. Imported responses must bind to the exact ephemeral requester and latest observed 10044 before durable custody/activation. Requests are freshness-bounded and completed IDs are journaled. See [automatic key sync](docs/KEYS.md#automatic-same-identity-key-synchronization).

Own metadata subscriptions and peer cache hold only verified signed state; newest observed does not mean globally fresh. Stale peer routes/keys can temporarily remain in use within the documented cache window. Missing peer 10050 uses own DM relay fallback, so peer receipt is not guaranteed. Metadata snapshots are instance-local memory; durable seal/declaration ordering remains in the existing store. Full lookup failures do not establish a successful absence; fallback after total failure requires existing authenticated key evidence.

Construct a Bot with a signer. Its startup resolves the account through Signer.getPublicKey and uses Signer.signEvent and NIP-44 operations. Signer implementations keep the credentials, and the application owns their lifetime. Receipt callbacks registered with `observe()` receive detached snapshots. Use durable handlers for business effects, with application idempotency where retry can repeat an effect.

Startup command reconciliation uses author-scoped kind 31992 snapshots only; signature/author checks and detectably incomplete-read failures remain mandatory. Fresh absence does not make confirmed local cache into remote presence. Relays can silently omit/cap results, and public operations across replicas are not atomic. Independent discovery still verifies kind 5 withdrawals to exclude stale definitions. Unsupported legacy journal event kinds are dropped before replay; supported pending command operations retain exact IDs.

The optional official allowlist is an inbound identity policy, applied only after cryptographic identity binding and before incoming persistence/evidence/observers, with rechecks for old pending work. It receives a sender string, not a mutable message. Legacy restrictions and a new policy compose restrictively; non-boolean/async results never grant access. Official requestTiming telemetry contains only elapsed milliseconds and chain outcome, reads no message/error context, and isolates observer failures. Custom policies and observer implementations remain application-owned; ordinary business middleware cannot provide pre-persistence denial guarantees.

Public kind 1/1111 input requires an explicit inbox and declared supported scopes. Signature, source, author policy, structure and unambiguous invocation targeting are checked before the separate public journal or business middleware. Public session/thread methods never load private peer data. Public replies are intentionally public kind 1111, routed only to configured write/source relays; arbitrary tag URLs are not contacted. Public thread scope claims are signed claims, not proof of truthful ancestry, and resolved context remains untrusted application input. Public ID deduplication retains at most 5000 records; eviction, failed handlers and uncertain completion prevent an exactly-once guarantee. Public queued payloads/outbox use the same selected storage codec as internal metadata. See [public input boundaries](docs/PUBLIC.md).

Delayed `bot.reply(event,...)` / `bot.thread(event,...)` calls use original input events, never arbitrary IDs or outer envelopes. Signed public events are independently reverified; source provenance is local-journal-only. Unsigned DM rumors must match the account/mode's persisted authenticated incoming record, canonical hash/fields and private routing; a rumor's ID or asserted sender alone grants no trust. Applications own their worker queues and must protect saved DM events as plaintext. Calls are explicit application effects, not inbound policy dispatch; repeated calls are not deduplicated as jobs. See docs/API.md.
