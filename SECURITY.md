# Security policy

Chirli is experimental. It has not had an independent security audit. No supported-release or response-time commitment has been established.

## Reporting

Use GitHub's private vulnerability reporting form to contact the Chirli maintainers. [Report a vulnerability](https://github.com/CodyTseng/chirli/security/advisories/new)

Include the affected version and mode, expected and actual behavior, impact, sanitized diagnostics and a minimal local reproduction with disposable keys. Keep live credentials and private messages out of reports. Use the private channel for vulnerability details.

## Boundaries

- The decoder verifies the giftwrap, seal, rumor hash, author and one-to-one recipient before exposing text. Default identity-key NIP-17 and explicit split-key mode both accept verified standard and NIP-4E envelopes; the legacy compatibility:false flag only suppresses identity-key declaration publication. Known unrelated own key declarations block publication; discovery freshness is bounded by relays/cache, not globally guaranteed. See docs/INTEROPERABILITY.md.
- Database payloads use AES-256-GCM only when storageKey is supplied; otherwise payloads/keyrings are explicitly tagged plaintext without cryptographic tamper protection; routing metadata, claimed IDs and status/timestamp indexes remain visible. Core Bot does not store identity signing secrets; the live application can persist a generated signer in a private adjacent file. Split encryption keys and pending declarations follow the configured plaintext/encrypted codec. Preserve the original storageKey whenever encryption is enabled. Protect storage keys, files, backups, process memory and your own logs. Downloaded attachments are saved as verified plaintext in a separate per-account directory; `storageKey` protects database payloads only. Attachment downloads are explicit and limited to configured origins, including each redirect.
- Authenticated canonical input IDs are claimed atomically before business middleware. Claims prevent a second SDK attempt, not missed or partial effects after a crash. The SDK does not retry business callbacks. Relay acceptance means neither delivery nor reading.
- Incoming DMs before first activation are ignored. Eligible incoming DMs found during downtime recovery can execute the same middleware and handlers as live input, but never rerun a claimed ID. Outgoing self copies and public history do not run business handlers.
- Untrusted relay URLs come from signed metadata or application configuration. The SDK makes outbound WebSocket connections to them; applications deploying in restricted networks must enforce their own destination policy. There is no built-in SSRF allowlist or tenant boundary.
- Identity signers must sign the exact requested template. Both modes retain identity-key crypto for standard peers; split mode adds generated/imported current, pending and legacy local keys. Neither mode supplies forward secrecy or key-vault isolation by itself.
- Error observers can see verified message context and application errors. Observer failures are ignored so monitoring cannot crash message processing; sanitize logging and handle telemetry failures in your application.

One active process/client per account database, including across modes, is supported. Synchronous storage and crypto execute on the Node thread, and received-event history/dispatch queues are not a production-grade resource admission system. Full archive enumeration, undecryptable-envelope retention, storage-key migration, distributed workers and application authorization are outside this MVP. See README and API.md before deployment.

The checked-in CI uses only disposable/local protocol tests. Actual public relays, mobile apps, external bunker products and hardware signers and production deployments require separate assessment. No real AI provider or external tool execution is part of this SDK.

Managed subscriptions reconnect with bounded backoff and overlap paging; raw transport alone does not. Recovered DMs since first activation are eligible for a first dispatch, and incomplete scans leave checkpoints unchanged. A remote signer sees plaintext used in NIP-44 operations. Its operational failures are surfaced and stop recovery checkpoint advancement. Opaque remote decryption errors are conservatively treated as retryable, so corrupt signed wrappers can also leave a remote scan incomplete; there is no durable raw-envelope quarantine or product-specific error classification. See SIGNERS.md and RECOVERY.md.

Registered NIP-CD definitions are always public on configured write relays. Bot startup reconciles its account's complete registry, including deleting old definitions absent locally. Register every module before starting one account owner. Ordinary Clients do not own catalogs or modify user-installed kind 10992 lists. All write-relay queries/publications must succeed before Bot startup completes. An unavailable or known truncated snapshot never becomes deletion evidence. Metadata/scopes grant no execution permission, and public withdrawal cannot erase cached copies.

Explicit keyRotation configuration authorizes scheduled public encryption-key declarations while started. Candidates are durable before publication; ACK failure keeps pending custody and retries the same event. Retired-key count/optional age pruning happens only after successful rotation. Evicted keys cannot decrypt unseen old envelopes; SQLite/WAL/backups are not securely erased. Known foreign declarations require explicit locally held-key migration, never forced overwrite. Relay/cache checks are not a globally fresh account lock. See [key custody and migration](docs/KEYS.md).

Custom MessageStorage implementations receive retained encoded private messages, diagnostic state and routing metadata, never storageKey, keyrings, evidence or outbox records. They are trusted for durable unique insertion, state updates and account isolation. The SDK records input claims separately in internal SQLite. With storageKey, payloads are ciphertext; without it they are readable plaintext. Internal SQLite retains only temporary message handoffs until insertion succeeds. Protect both stores and follow docs/STORAGE.md. Multiple-relay discovery can be partial; cached evidence is not a globally fresh declaration guarantee. At least one ACK is not all-relay replication. See docs/RELAYS.md.

Register allowlist as the first middleware to restrict downstream callbacks to verified accounts. Anonymous wrapper authors and split messaging keys grant no authorization. An empty list blocks every external sender from routing; omitting it imposes no additional access restriction. Eligible IDs remain claimed even for denied inputs. A short-circuited DM does not enter private history; recovered copies do not bypass this by storing a body. Crypto and remote signer work can occur before the sender is known. Middleware is not an outbound ACL or rate limiter. See [access](docs/ACCESS.md).

The optional live-example initializer creates a fresh bot nsec/storageKey in an ignored 0600 .env file; this is operator credential storage, separate from SDK keyring persistence and not a hardware vault. Live runners intentionally read operator configuration only when explicitly started, publish their own key/relay metadata and registered public commands and respond to permitted DMs. They do not print incoming text, credentials or bunker authorization URLs. Protect config/database backups. Automated tests use generated temporary configs and local relays only.

Zero-config live startup reuses/creates a 0600 identity file beside the database and logs only public keys. That file is encrypted if CHIRLI_STORAGE_KEY is provided, otherwise plaintext. It is never overwritten to fix parsing/key/mode errors. Existing databases without their generated signer file require the original signer to avoid silently changing accounts. Default public relays match PsstPsst; testing does not connect to them. Plaintext persistence assumes trusted filesystem/backend contents, including retained conversation records and claim IDs. Initial wire signature/author validation and NIP-44 encryption remain mandatory in either storage mode.

Built-in RelayError diagnostic fields expose only origin, operation/code, whitelisted network/reason codes and numeric statuses/kinds. Relay paths/queries/credentials, raw rejection bodies, AUTH challenges and message text are withheld. The live formatter does not print arbitrary application Error.message/stack and bounds aggregate recursion. Explicit custom application logging remains the application's responsibility. Read-only operator connectivity diagnostics do not require a private key or event publication.

Automatic NIP-4E device sync is enabled by default. Only verified requests signed by the exact account identity can export held separated keys, and only encrypted 4455 responses are published. Identity signing secrets are excluded. This headless policy authenticates signing capability, not human presence; permission to sign 4454 is secret-transfer authorization. Use keySync:false / CHIRLI_KEY_SYNC=0 if this is unsuitable. Imported responses must bind to the exact ephemeral requester and latest observed 10044 before durable custody/activation. Requests are freshness-bounded and completed IDs are journaled. See [automatic key sync](docs/KEYS.md#automatic-same-identity-key-synchronization).

Own metadata subscriptions and peer cache hold only verified signed state; newest observed does not mean globally fresh. Stale peer routes/keys can temporarily remain in use within the documented cache window. Missing peer 10050 uses own DM relay fallback, so peer receipt is not guaranteed. Metadata snapshots are instance-local memory; durable seal/declaration ordering remains in the existing store. Full lookup failures do not establish a successful absence; fallback after total failure requires existing authenticated key evidence.

Construct a Bot with a signer. Its startup resolves the account through Signer.getPublicKey and uses Signer.signEvent and NIP-44 operations. Signer implementations keep the credentials, and the application owns their lifetime. Receipt callbacks registered with `observe()` receive detached snapshots. Use an application-owned durable job or idempotency mechanism where a business effect must recover after a crash.

Startup command reconciliation uses author-scoped kind 31992 snapshots only; signature/author checks and detectably incomplete-read failures remain mandatory. Fresh absence does not make confirmed local cache into remote presence. Relays can silently omit/cap results, and public operations across replicas are not atomic. Independent discovery still verifies kind 5 withdrawals to exclude stale definitions. Unsupported legacy journal event kinds are dropped before replay; supported pending command operations retain exact IDs.

`requestTiming` telemetry contains only elapsed milliseconds and chain outcome, and isolates observer failures. Applications own their policies and observers. No access middleware runs before authentication and the ID claim.

Public kind 1/1111 input requires an explicit inbox and declared supported scopes. Signature, source, structure and unambiguous invocation targeting are checked before claiming an ID and running business middleware. Public session/thread methods never load private peer data. Public replies and reactions intentionally publish signed kind 1111 and kind 7 events, respectively, only to configured write/source relays; arbitrary tag URLs are not contacted. Public thread scope claims are signed claims, not proof of truthful ancestry, and resolved context remains untrusted application input. No public input history or callback payload is kept. Claims do not guarantee exactly-once external effects. The public outbox uses the same selected storage codec as internal metadata. See [public input boundaries](docs/PUBLIC.md).

Delayed `bot.reply(event,...)`, `bot.react(event,...)` and `bot.thread(event,...)` calls use original input events, never arbitrary IDs or outer envelopes. Signed public events are independently reverified; only immediate handler calls retain the incoming relay as a routing hint, and delayed replies and reactions use configured write relays. Unsigned DM rumors must match the account/mode's persisted authenticated incoming record, canonical hash/fields and private routing; a rumor's ID or asserted sender alone grants no trust. Applications own their worker queues and must protect saved DM events as plaintext. Calls are explicit application effects, not inbound policy dispatch; repeated calls are not deduplicated as jobs. See docs/API.md.

The nostr-tools transport uses a native JSON syntax preflight and canonical EVENT framing to prevent malformed inputs from reaching the dependency raw logger. Non-string CLOSED reasons are normalized to a constant safe rejection. The library uses an origin-only diagnostic label while the socket and NIP-42 tag preserve the exact configured URL. Tests cover malformed/truncated EVENT and control JSON with synthetic token/content values. This framing guard adds one native JSON decode before library decoding; it is not an independent Nostr parser or a guarantee about all future dependency diagnostics. See docs/RELAYS.md for tested boundaries and remaining ACK/keepalive timer behavior.
